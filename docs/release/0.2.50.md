# 0.2.50 — Separate native Metal host

The renderer, caches and shader translation can now run in their own ARM64 process,
while game code and networking continue under Rosetta. Guest allocations, releases,
address reuse and reclamation ownership are synchronized across the process boundary;
missing history disables reclamation rather than risking a live resource. Shared guest
memory stays mapped without creating another full copy.

- Default on in supported macOS 27+ packages. Advanced Metal options include **ARM64
  renderer host** for returning to the old path. macOS 26 retains the old path.
- F3 stops and reaps the old renderer before restarting offline. The game keeps its
  cover icon; the forwarding process does not add a Dock entry.
- Fix a scheduler dependency exposed by native execution across empty render passes.
  Existing two-level addressing, velocity/blur bypass, occlusion, texture-format guards,
  memory budgets, Chinese translation and online routing remain in place.
- Eight matched M4 runs averaged 44.64 → 47.27 FPS (+5.9%); 1% low 34.29 → 39.52.
  Combined accounted process footprint was about 270 MiB lower. This is one fixed
  scene and does not establish 60 FPS everywhere. No quality or cache-capacity reduction.
- A follow-up retaining the owner’s extra experimental flags measured 50.62 / 45.94 FPS
  (native / fallback); accounted footprint was about 52 MiB higher, with equal pressure
  and no scored swap growth. This short pair is separate from the eight-run result.
- Isolated recovery and consecutive respawns passed. Keyboard mapping and networking
  routing tests passed; physical F3, enemy-combat coverage and fresh live-server testing
  are separate coverage limits. Normal saves, settings and existing caches are preserved.
- Full source build now builds and packages both Metal host architectures. Native
  dependencies are checked for architecture, minimum OS and self-contained load paths.

See [ownership, build and measurement details](ARM64-METAL-EXPERIMENT.md).
